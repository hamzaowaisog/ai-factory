## The ticket
> Cancelling a completed appointment, or completing a cancelled one, returns 400 Bad Request. The request itself is valid; the appointment's current state forbids it, so the API should answer 409 Conflict with the same error message. A missing or too-long reason or notes must still return 400.

A real gap in the public repo; no planted bug. The right fix is `Error.Validation` → `Error.Conflict` in two handlers.

## Before the run: the $0 rehearsal
Pre-flight ran a dry run of this exact ticket on this repo with scripted model answers. Everything else was real: lab,
containers, gates and delivery, with no forge configured. It caught four problems that would each have failed the
paid run after money was spent:
1. `factory init` couldn't read the target framework from `Directory.Build.props`, which both pinned public repos use. Fixed: 16a46b6.
2. The accept step would have crashed booting the app. Fixed in the project config (see Accept above).
3. **A factory bug.** A flaky test that passed on re-run left the first run's exit code 1 with no failed test, so the evidence was judged invalid and the run parked as a "safety" failure. Fixed: 3cad10f.
4. **A bug in the repo's tests.** Parallel test classes seeded one shared in-memory database and collided ("An item with the same key has already been added"). Fixed in the fork: 03e3ecb, one database per test factory.

The second dry run delivered: 33/33 tests, locked tests passed on the first implement attempt, $0.

### Spec and plan
- **Spec:**
  - REQ-1: cancel a completed appointment → 409 with the domain message.
  - REQ-2: complete a cancelled appointment → 409 with the domain message.
  - REQ-3: the OpenAPI metadata declares 409. This was not asked for.
  - REQ-4: a missing or too-long reason or notes stays 400 in any state.

  The round trip matched the request (nothing dropped, nothing added).
- **Plan, size M:**
  - TASK-1: `Error.Validation` → `Error.Conflict` in both handlers.
  - TASK-2: `.ProducesProblem(409)` on both endpoints.
  - TASK-3: put the description into `ProblemDetails.Detail` too. This was also not asked for; it's additive.
- **Code delivered:** 17 production lines across 4 files, matching the expected fix plus the two additions.

## Impact step replay (free research data)
The ripple-effects code layer (PR #16) was replayed on this run's ledger: 158 ms, no model calls.
- **Grounding already had every production file the run changed** (4/4 were seeds).
- New test files can't be flagged (they didn't exist); the one modified test file was flagged as "check".
- The plan check passed.
- **False alarm.** Risk was raised low → **high** ("reaches stored data: Appointment") because grounding cited the domain
  class `Appointment.cs` as context. That pulled its DbSet, EF configuration and migrations into the card's
  "Will also affect" list. The change touched no stored data.
